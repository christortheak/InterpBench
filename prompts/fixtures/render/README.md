# Golden render fixtures (cross-engine, both model families)

Committed, git-versioned golden fixtures for **prompt rendering + tokenization**
— the documented #1 cross-engine correctness risk (Gemma's no-system-role
folding, double-BOS when a chat-template render meets a second
special-token-adding tokenization, Qwen3's no-think template).

Authoritative source: the **Python engine's tokenizer path**
(`Server/steerlab_server/experiment/prompt_render.py` via the server venv's
`transformers`), loaded from the local HF cache with `local_files_only=True`.
Generated by [`generate.py`](generate.py); regenerate from the project root:

```bash
Server/.venv.nosync/bin/python prompts/fixtures/render/generate.py
```

A tokenizer/template upgrade that changes any `rendered` string, `tokenIDs`,
or `bosCount` shows up as a git diff here and as a **loud test failure** in
`Server/tests/test_golden_render_fixtures.py` and
`Tests/ExperimentKitTests/GoldenRenderFixtureTests.swift` — never a silent
skip. Commit a regenerated fixture only after understanding the diff.

## Models pinned

| Family | fp repo (tokenizer reference) | MLX repo (what the Swift engine loads) |
|---|---|---|
| qwen  | `Qwen/Qwen3-0.6B` | `Qwen/Qwen3-4B-MLX-4bit` |
| gemma | `google/gemma-3-4b-it` | `mlx-community/gemma-3-4b-it-4bit` |

The MLX repos' tokenizer configs **did** load through the Python `transformers`
tokenizer from the cache, so both engines' actual token ids are covered.
Verified at generation time (2026-07-06, transformers 5.12.1): for every case,
the fp repo and its MLX counterpart render **byte-identical strings and
identical token ids**.

## Cases (per model)

| case | renderer API | what it pins |
|---|---|---|
| `chat_plain` | `render` (chatAssistant) | plain single user prompt |
| `chat_system` | `render` (chatAssistant + system) | **Gemma system-text folding** into the first user turn; Qwen system role |
| `chat_multiturn_system` | `render_messages` (2 user + 1 assistant + system) | multi-turn template + Gemma first-user-turn folding |
| `qwen_nothink` (qwen only) | `render` (chatAssistant, thinking off) | the Qwen3 no-think template (`<think>\n\n</think>` generation prompt) |
| `raw_completion` | `render` (rawCompletion) | tokenizer-default BOS; Qwen ` /no_think` suffix. **Known cross-engine divergence — see below.** |
| `chat_seeded_assistant` | `render_messages` (user + seeded assistant + user) | send-as-assistant: the `seeded: true` provenance flag is INERT for rendering (generator asserts byte-identity with the flag-stripped twin AND with an `edited: true` twin — both provenance flags are invisible to the template) |
| `chat_assistant_first` (qwen only) | `render_messages` (seeded assistant first, then user) | assistant-FIRST transcripts render on the permissive family (Qwen). Gemma's template enforces user-first strict alternation (`Conversation roles must alternate…`), so no gemma fixture exists BY DESIGN — the refusal is pinned by the live-template constraint tests (`Server/tests/test_seeded_turns.py` / `GoldenRenderFixtureTests`) against `conversation_constraints` / `ExperimentTasks.conversationConstraints` |
| `chat_prefill_continue` | `render_messages` (`continueFinalMessage`) | assistant-prefix continuation: transformers' `continue_final_message` render, ends exactly at the seeded prefix (no end-of-turn, no generation prompt); the Swift sentinel-mirror (`ExperimentTasks.continuationRender`) must reproduce it byte-for-byte |
| `study_transcript` | `render_transcript` (system turn + user + seeded assistant + user) | the scripted-transcript STUDY instrument: the pinned transcript renders through `render_messages` / Swift `studyUserInput`→`transcriptMessages` (the same path both study run loops call); the recorded `systemPrompt` is a DECOY — the transcript's own system turn REPLACES the study system prompt (the composition rule), and the seeded flag stays inert (both asserted at generation time) |
| `reader_scaffold` | `render_reader` | RepE reader scaffold stays plain text; extractor tokenization (`add_special_tokens=True`, single BOS) |

## Fixture schema

```json
{
  "family": "gemma",
  "modelID": "google/gemma-3-4b-it",
  "case": "chat_system",
  "inputs": { "api": "render|render_messages|render_reader", "...": "exact renderer arguments" },
  "rendered": "<exact prompt string>",
  "tokenIDs": [2, 105, ...],
  "promptTokenCount": 31,
  "bosCount": 1,
  "bosTokenID": 2,
  "generator": { "transformersVersion": "...", "tokenizerClass": "...", "generatedOn": "..." }
}
```

`bosCount` is the number of consecutive BOS tokens at the start of `tokenIDs`
— the double-BOS tripwire. Expected: **Gemma = 1 in every case (with and
without a system prompt); Qwen = 0 in every case** (Qwen3 has no BOS token).

## Known convention divergence (Gemma system text, multi-turn)

The `chat_multiturn_system` fixtures pin the SERVER transcript convention:
Gemma's system text folds into the FIRST user turn only
(`prompt_render.render_messages`). The Swift interactive chat surface
(`ChatService` → `ChatSession`) prepends the system text to EVERY user turn
(`chatPrompt`), and its seeded-history replay adapter
(`ExperimentTasks.chatHistoryMessages`) deliberately reproduces that per-turn
fold so replays match what the model actually saw. Interactive-chat
transcripts and server study renders are therefore not byte-comparable for
Gemma + system prompt; measured runs use the single-prompt `render` path,
where the engines agree.

## Known cross-engine divergence (rawCompletion)

The `raw_completion` fixtures record the **Python** engine's behavior: no chat
template, `add_special_tokens=True` (tokenizer-default BOS), Qwen gets a
literal ` /no_think` suffix. The Swift engine's rawCompletion path
(`ExperimentTasks.userInput` → `UserInput(prompt: .text(...))`) is routed by
mlx-swift-lm's `LLMUserInputProcessor` through `messageGenerator.generate` →
`applyChatTemplate`, i.e. the "raw" text is wrapped in a user chat turn — and
without `additionalContext`, so Qwen's `enable_thinking=False` is not passed
either. The two engines therefore feed **different token sequences** to the
model for rawCompletion. The Swift test pins both current behaviors and fails
loudly if either side changes; do not treat cross-substrate rawCompletion runs
as comparable until this is reconciled. (chatAssistant, the study default, is
byte-parity across engines — that is what the other cases assert.)
